# 切断重连、浏览器指纹与 HTTP 协议专项（2026-10-22）

## 结论

**切断后切换浏览器指纹或 HTTP 协议在技术上可行，尚未证明能提高这条线路的成功率。** 五组各五轮，共 25/25 完整下载并通过 SHA256；其中 20 次强制切断全部取得正确的 206、确认同一资源并成功续传。原连接继续的中位耗时 5.434 秒，所有主动切断组的中位耗时都更长。默认下载策略保持不变。

这轮没有复现此前约 19 KiB/s、被外部 45 秒基准总时限终止的严重慢传。不能把“强制切断后完成”写成“自然慢连接被成功修复”。旧失败和阶段排查仍保留在[此前报告](link-investigation.zh-CN.md)，不合并分母或改写为成功。

## 方法和绑定

- 实验源码提交：`0f680196e506e2b83e58102ba86a199ae38583c3`。运行前源码干净。实际 `reconnect_probe` SHA256：`70d481fd2d36ee09d80ce9b79dd7ce06d9d7132e7bb3aa88ed1f908d66bceccc`；调度脚本 SHA256：`b18336252eecd522ff7690db5e4578159de149c8cce4ce4abf1a76c38033f782`。末次源码提交只修正 TCP 采样方式，Rust 示例与实际构建时的前一提交相同。
- macOS 27.0.1、Darwin arm64；wreq 6.0.0-rc.31、wreq-util 3.0.0-rc.14。该示例直接使用当前传输依赖和 SDK 的资源身份校验模块，**是传输实验，不是完整生产 CLI 或全套 SDK 下载流水线验收**。未改生产库或 CLI 的指纹/协议/重试默认值。
- 同一个公开 [MDN flower 视频](https://interactive-examples.mdn.mozilla.net/media/cc0-videos/flower.mp4)，1,128,375 bytes；SHA256 `0cd83d944a6ca7822b4a8306cecc60a36e859b041f6702c6a1ad9ead78924451`。每次单文件、单连接，五组按五轮循环轮换位置；无预热下载，不并行跑其它下载基准。
- 原生显式绑定物理网卡，`.no_proxy()`，公开 DoH 只解析一次并固定同一公开 IP；无转发器、系统 DNS 回退或外部代理。485 行测试连接采样核对全部在该物理接口且只有一个远端 IP。原始地址/端口及 DNS 映射不公开。
- 初次统一 Chrome131/HTTP2、匹配 Windows Chrome131 UA、完整 GET。四个重连组保留前 256 KiB 后丢弃响应与 Client，新建 TCP/TLS 连接；其余组分别切换真实 Chrome149/Firefox144 仿真配置或 HTTP1.1，UA 随浏览器版本匹配。**仿真配置包含 TLS/HTTP2 设置及匹配 UA，不是只改 UA，也不能从此实验单独分离出 TLS 一项的因果效果。** HTTP1.1 切换也必然改变 ALPN/协议行为。
- 重连均发相同 Range/If-Range，强 ETag 和准确 Content-Range 必须匹配；返回 200 时清空旧字节安全重下，身份/区间冲突硬失败。完整文件随后独立核对长度和 SHA256。该原则遵循 [RFC 9110 的 Range/If-Range 语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5)。
- 主表时间覆盖初次建连、首段正文、中断、再次握手和剩余正文；示例将小文件存于内存，**计时不含最后落盘/原子改名或 SHA256**。每次 60 秒诊断总预算，外部 70 秒兜底；不能把它当成库默认总超时。Python 观察器收尾时间单独记在 wall_elapsed_s，不用于主表。

## 正式五组结果

| 处理方式 | 完整成功/计划 | 中位传输耗时 s | 最快–最慢 s |
|---|---:|---:|---:|
| 原连接继续：Chrome131 / HTTP2 | 5/5 | 5.434 | 4.186–12.205 |
| 切断后同指纹：Chrome131 / HTTP2 | 5/5 | 9.636 | 9.142–10.500 |
| 切断后 Chrome149 / HTTP2 | 5/5 | 8.779 | 6.759–11.863 |
| 切断后 Firefox144 / HTTP2 | 5/5 | 13.096 | 9.475–15.826 |
| 切断后 Chrome131 / HTTP1.1 | 5/5 | 9.148 | 6.824–11.119 |

所有 25 个初次响应均是 200/HTTP2；15 个重连响应是 206/HTTP2，5 个是 206/HTTP1.1。没有 403、429、挑战页或身份校验冲突。退出码 0 本身不计成功，必须同时有 complete、完整长度和正确摘要。[逐条结果、速率时间线和程序哈希](reconnect-results.json)

相对“同指纹重连”，Chrome149 的中位数约短 9%，HTTP1.1 约短 5%，Firefox144 在本组更慢；样本数只有各五次且范围重叠，初段也存在网络波动，不能把差值当成稳定收益或断言某浏览器必然更好。五组全成功，也没有成功率提升可计算。原连接继续从 4.186 到 12.205 秒的变化，已足以提醒我们不要用一次快慢决定默认协议。

## TCP 侧进一步定位与独立 curl 控制

只对测试子进程使用 nettop，记录接收、重复/乱序字节、客户端发送重传、RTT 和接收缓冲。公开结果是每次连接采样到的累计计数最大值；不把同一 socket 的多次采样相加，也不把两个重连 socket 混成一个传输总数。采样可能错过最后一个瞬间，所以不能把 max_received_bytes 当成精确线速总流量。

正式 25 次全部记录到非零 TCP 接收乱序字节：每次的最大值为 680,772–1,088,999 bytes，中位数 785,608 bytes。每次采样 RTT 最大值为 231.28–560.88 ms，中位数 294.16 ms。客户端发送重传计数为 0 **不代表下载方向没有丢包/重传**；服务端发送统计没有提供。

随后独立执行系统 curl 8.7.1，HTTP1.1/HTTP2 两轮倒序，不与上述实验并发。相同公开视频、匹配 Chrome131 UA、完整 GET、独立公开 DoH 快照固定 IP、显式物理网卡和 `--noproxy '*'`，无强制中断、总预算 60 秒；全部完整 SHA256 通过。它使用系统 SecureTransport/LibreSSL，作为不同客户端实现的诊断控制；未把它纳入五组速度排名。[curl 原始数值字段](reconnect-curl-control.json)

| 轮次 | 实际 HTTP | 首字节 s | 总耗时 s | 接收乱序最大 bytes | RTT 最大 ms | 完整摘要 |
|---|---|---:|---:|---:|---:|---|
| 1 | 1.1 | 2.122 | 23.125 | 852,583 | 289.25 | 通过 |
| 1 | 2 | 1.577 | 10.886 | 1,001,555 | 301.31 | 通过 |
| 2 | 2 | 1.615 | 4.399 | 1,065,962 | 549.00 | 通过 |
| 2 | 1.1 | 1.019 | 9.987 | 1,022,505 | 249.22 | 通过 |

**能进一步确认的是，两套客户端都在共用的 TCP 接收路径上观察到大量乱序记录和明显的耗时波动。** 结合此前 curl 的 200 后慢传，排查重点应放在传输路径/服务侧传输行为，而不能只归为 Rvdown 的 TLS 指纹失效。

但乱序累计字节数不能除以文件大小当“丢包率”，也不能证明它就是此次耗时的全部原因；较快的样本也有大量乱序记录。现有证据无法区分真实包乱序、缺包后的重排、本机接收栈表现，或进一步锁定哪台路由、运营商/CDN 整形。200 同样不能排除隐式限速。要定位具体责任点，还需要同一慢传时段的定向包序列证据和独立网络出口对照；当前仅有一个出口，不补造确定归因。Apple 提供的 [TCP 连接指标](https://developer.apple.com/documentation/kernel/tcp_connection_info)与[包跟踪方法](https://developer.apple.com/documentation/network/recording-a-packet-trace)可用于进一步验证。

## 样本来源和代理环境的边界

本轮 25 次及后续 4 次 curl 都只用 MDN 公共示例媒体，没有使用 GitHub 下载地址。此前 FFmpeg/Samplelib 属于公共样本站，不能统称为真实业务平台的视频 CDN；GitHub raw 是单独的镜像诊断，不进入本轮排名。自建回环 HTTP 夹具只验证续传、低速退让与媒体功能，不作为公网线路速度证据。境外样本站慢不能直接证明真实视频 CDN 的反爬不足。

`no_proxy`/`--noproxy` 只表示程序不使用显式代理，不能单独证明避开宿主透明隧道。若宿主开启 TUN，需同时核对目标 IP 的普通/scoped route、测试 PID 实际接口，以及隧道连接视图的域名/IP；仅在代理内部选择 DIRECT，也不等于完全绕过其接收栈。本轮保留的事实证据是显式物理接口绑定、固定公开 IP 和逐 PID 接口采样，不对未监控的历史连接作绝对保证。[Mihomo TUN 路由机制](https://wiki.metacubex.one/en/config/inbound/tun/)

本机代理的实际规则、节点、控制接口秘密与内部地址不属于可发布的基准输入，不收集进公开证据文件。

## 对默认策略的决定

不定时切连接，不默认轮换浏览器，不强制所有来源 HTTP1.1。已有的可选持续低速保护与调用方提供的可信备用直链，仍是目前已做受控验证的退让路径，见[低速策略实验](link-investigation.zh-CN.md#已实现的改进可选持续低速保护)。本次新增示例和可复现实验入口，**尚未把“低速后自动换指纹”接入生产重试逻辑**。对具体站点的 403 或自然慢传恢复，需要保留同指纹重连对照再评估。

离线检查：默认 Rust 测试 175 项通过；示例资源一致性测试单独 2 项通过；Python 基准/边界测试 14 项通过；clippy 全 targets 零告警、fmt 通过。正式强制中断实验 25/25、独立 curl 4/4，与校准试跑分开统计；先导试跑不加入正式分母。未宣称更换协议解决所有 CDN 问题，也不替代其它来源/平台的实测。

本报告只发布公开来源、显式构造的数值字段和通用实验代码；原始 TCP CSV、地址/端口、日志、环境、凭据和媒体不入库。所有本轮成功下载媒体已清理。
